# TAS - Traveller Aid Software

This software presents a collection of command line tools to simplify working with the Mongoose Traveller 2E Update 2022 Roleplaying game.

# Command Directory
The sections below detail the various commands and their options.
You can always get help by executing `> tas -h` or `tas <command> -h` for help on a specific command.

### Global Flags
These flags are available to every command  
`--loglevel <debug|info|warn|error|fatal>` flag can be used to set log level.
The default logging level is 'warn'  
`--tofile` when set, writes the output to a local output folder.
Output is in JSON, but is indented to make it easy to read

## world
The `world` command generates details of one or more worlds as expressed on pages 246 - 261 of the core rulebook.
Output is either a standard Universal World Profile (UWP - see pg 248) or a full-text display of the meaning behind each code.
Note that several option calculations: bases, temperature, factions, and culture are not calculated. These details existed in previous versions of this code, were determined to be not useful, and just cluttered the world longform profile with information that is probably better determined by the GM on a case-by-case basis.

Usage: `> tas world [count] [flags]` where  

&nbsp;&nbsp;&nbsp;&nbsp;count is the number of worlds to generate. The default is 1.  
&nbsp;&nbsp;&nbsp;&nbsp;Flags:  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;`--long`  generate longform output instead of UWP.
Omitting this flag produces only UWP output  

## world debug (world sub-command)
The `world debug` sub-command isn't directly useful to sector designers, but instead is used to display the average stats of 40 (optionally: 10,000) randomly generated worlds.
This command exists to show averages and other stats for the randomly generated worlds in order to provide some insight into how well the rules-as-written generates random, believable, useful worlds.
Manual testing during development revealed that the worlds generated using the tables in the book had certain undesirable traits, including worlds with no atmosphere but meaningful water content and worlds with high populations or extreme environments yet very low tech levels.
The tech level algorithm is especially disturbing, as the rules as written generate an average tech level of 5 (mid 20th century tech), hardly sufficent to explain the hundreds of thousands of people living on an otherwise lifeless rock with no atmosphere.

The `world debug` sub-command is very useful for examining how a proposed algorithmic change to world generation actually impacts the kinds of worlds being generated.

Usage: `> tas world debug [flags]` where  

&nbsp;&nbsp;&nbsp;&nbsp;Flags:  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;`--worldscheme <standard|custom>`
If this flag is included, one of the two options must be provided.
The default is 'standard' and uses the rules as written to generate worlds.
The 'custom' option utilizes a slightly different algorithm to generate more believable worlds.
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;`--max`
If this flag is included, 10,000 worlds are used to generate stats rather than 40 (the averge number of worlds in a typical subsector). The differences between these are usually slight

Note: this command ignores the global `--tofile` flag!

## sector
The `sector` command generates a subsector (8x10 hex grid), creating full world details, establishing the presence of gas giants and the like.
The approach taken is to use the algorithm for world density and gas giant presence as expressed on pg 246.
This is accomplished largely by generating a set of random worlds with names and sub-sector locations, which uses the algorithms expressed by the `world` command above.
Since this command uses the world generation described above, it uses several of the same flags as well as the global flags.

Usage: `> tas sector <sector-name> [flags]` where  

&nbsp;&nbsp;&nbsp;&nbsp;sector-name is required and is the name of this sector  
&nbsp;&nbsp;&nbsp;&nbsp;Flags:  

If the global `--tofile` flag is used, a folder with the sector's name is written into the output directory and all world related-data is written into individual files in this folder.

## system
The `system` command generates a single solar system based on the UWP of the main world (as generated by the `world` command) and other critical data.

It is important to note that the intent of this mechanism to to present a mostly-believable solar system when players ask "What are the other planets like in this system and where are they?"
GM's have full range to edit this information as they see fit, and are further highly encouraged to hand-build solar systems when the composition of the solar system is key to some story they are telling.
GM's are further highly encouraged to learn about solar system formation and constraints and the underlying physical principles if they want to build believable, composite solar systems. If a 'hard science feel' is less important, than do whatever you want; you are just as likely to be right as wrong given the incredibly diverse mechanisms at play in actual solar system formation!

This code is based on significant research into planetary and solar system development including star types, rocky planet mantel formation and plate tectonics, magnetic field generation via self-induction, planet size limitations and effects, atmosphere creation, replenishment and retention, solar wind, water creation, gas giant moon formation and diversity, asteroid field density and average sizes, and dozens of other cosmological topics of an astounding and fascinating variety, each more strange and more interesting than the last.
It turns out that solar systems are so incrediblty diverse and that cosmological chaos and pure, blind chance is so intense that one has to constrain the model significantly to get anything other than complete randomness out of the model.
Since the desire is for a 'reasonably hard science outcome where the presented system is at least mostly-plausible as a whole' and modelling cosmologically was unacheivable, many assumptions and constraints were made when creating this mechanism.
So, the solar systems presented by this algorithm are pseudo-realistic, after making a bunch of assumptions, but they should work for quick content and pass a 'reasonableness test' for most players while providing table-ready gamable content for GMs without aggregious violations of basic physical principles or obvious contradictions (to non-scientists at least).

This code makes the following assumptions when creating these systems:
* All stars are Sol-like (Class G, specifically G2V). In reality, only 7% of the stars in our galaxy are of this class; the vast majority are Class M red dwarves. It might have been better to pick class K stars (orange dwarfs) as the 'best' star for colonization given its many advantages over a Class G star, but as players are familiar with our sun and no other, our sun class was chosen as the model.
This has a _huge_ impact on the way solar systems are formed, habitability zone location, radiation and luminosity profiles, order of planets and the like, but the intent is to provide a gamable baseline, not diverse cosmological models.
This was a neccessary assumption because things change radically as sun type / mass change. Intrinsicly, most players _think_ suns operate like our sun (they do not), and think of planets being somewhat illuminated and irradiated in ways in which they are familiar. The many assumptions in the code make these inherent assumptions a baseline convention to reduce variability and increase gamability at the table at the sacrifice of realism and hard science
* Traveller UWPs describe _size_ (e.g. planetary diameter) and conflates that with _mass_. This is a fair simplification for a game. This code does the same thing
* Whenever possible, this code uses what is known about solar system formation, exo-planets or our solar system to create these models.
Given this, all solar systems generated are both likely typical of Class G2V-based solar systems and somewhat like our own solar system at first pass but also aligned with general, current thinking on the makeup of solar systems.
As a concrete example of this, planet spacing (in AU) is roughly based on a Sol-like system (with variability) but gas giants never have bright rings (Saturn, as it turns out, is excpetionally rare!)
* No distinction is made between gas giants (Jupiter, Saturn) and ice giants (Neptune and Uranus); all such planets are "gas giants" as generated.
This is because RAW does not make a distinction, and both provide ample free hydrogen in their upper atmospheres for refueling purposes
* Gas giant and other moons count only orbital objects large enough to be spherical and to be considered at least dwarf planets.
No effort is made to create realistic clouds of orbitals, most of which are small, oddly-shaped rocks (Saturn has more than 285 'moons', only 7 of which are spherical and only a one of those, Titan, is 'planet-sized' - Size 5 in UWP terms - bigger than Mercury!)
* I did not allow for the formation of 'hot jupiters', deal with planetary migration, partial or complete tidal locking, advanced physics, or rare events (e.g. Venus spins backward because of atmospheric drag and Uranus was knocked sideways by an anceint impact)
* This algorithm liberally intermixes rocky planets with asteroid belts, which is likely not realistic for G2V-based solar systems with rocky inner planets and external gas giants. This was just to create more variety so every solar system was not identical. However, asteroid belts will not generate next to each other as that is highly implausible without some very strange external events
* Planetary sideral period (that is, the length of time it takes for a planet to rotate once on its axis) is not calculated, even for the main world (the UWP planet). GMs can make this whatever they want. Keep in mind that Jupiter spins once every 9 hours and Venus every 265-ish earth days. This is an entire field of study, and the rotational period has a huge effect on planetary appearance and behavior (think: massive windspeeds on Jupiter, though the lack of a rocky surface contributes to this). Planetary tags (see below) may convey or imply what these values should be
* Planetary orbital periods are based on mean AU from the star and Keplar's Laws. No Newtonian effects (e.g. star mass, other masses) are used to determine this information. All planetary orbits are assumed to be standard elipical paths with no pertubations
* The UWP world is required to be within the habitability zone of the star (assumed by RAW) and will _always_ be a rocky planet unless it is an asteroid.
This means the 'core planet' represented by the UWP will never be a moon of a gas giant, space station or something other than a basic planet or an asteroid.
This is not because this is not possible - it absolutely is, but is because of the next, critical point
* The UWP (by RAW) represents _the best planet in the solar system for colonization_; every other planet, moon or asteroid has to be _worse_ in some way.
This means that if the UWP is an asteroid, the other options are either non-existant (no other planets - even gas giants) or worse everywhere else, because living on a asteroid is a bad idea unless one has to


It is because of this last point that many other assumptions are made.
As a simple example, no other planets are placed in the habitability zone; to do so would beg the question "why not live _there_ instead of the planet described by the UWP?"
For the same reason, this code does not create UWPs for every other planet and moon; it would be far too hard to make them catagorically worse (whatever that means) than the provided UWP.
Instead, a tagging system is used to roughly describe each other planet and moon, with these tags almost unversally being 'something terrible that prohibits or strongly discourages colonization'.
All such tags are representative of features found in our solar system or that are scientifically plausible.
A fair amount of effort (but not a massive amount) went into selecting and catagorizing these tags to ensure they made sense when applied to a planet (e.g. a rocky panet close to the sun will _not_ have a tag implying liquid methane on its surface). 
This is where randomness is very harmful when telling a space story and why so many assumptions were made; the goal was pseudo-reasonable outcome, not choas for randomness' sake.
These tags might provide some indication of the degree of atmopshere, internal planetary heat and chemical makeup of a planet in lieu of a full UWP.
This tagging system is not perfect, use it as provided or feel free to remove tags you think are incompatible with one another.
At times these tags make it clear that an atmosphere is present, even if it is unpleasant or dangerous.
Of course, GMs are free to spread colonies across other places if desired (high TL can overcome many disadvantages) and change the makeup of the inner or outer planets, but the baseline goal is to make the UWP-planet the best choice for colonization if for no other reason that its location in the habilitability zone of benign G2V star.
It should also be noted that other planets might contain outposts, mines or other habitants and some planets or moons might be prime candidates for these kinds of settlements, but none will be randomly generated so as to make the GMs life easier; it is always easier to quickly add a small outpost than to remove one that is baked into the raw output of a generator. 

Usage: `> tas system <full-uwp> <distance> <gas-giant present> ` where  

&nbsp;&nbsp;&nbsp;&nbsp;full-uwp is the primary world's UWP with full trade and travel codes (this matters!)   
&nbsp;&nbsp;&nbsp;&nbsp;distance is the primary world's distance in AU from the sun. This must be between .95 and 1.67 inclusive (Earth is 1.0, use that if unsure, smaller values for hotter, bigger values for colder like Mars)  
&nbsp;&nbsp;&nbsp;&nbsp;gas-giant-present should be expressed as 'yes', 'no', 'true', 'false', 'y', 'n', 't' or 'f'. If true/yes, this means the system has a gas giant present

## polish
The `polish` utility command reads the ./data-local/world-names.txt file and performs the following clean-up on the file:

* Removes duplicate world names
* Trims excess spaces from world names
* Sorts world names alphabetically

It does this is a very safe manner (through the use of temporary files) so a huge list of world names is not accidently overwritten or discarded.

Usage: `> tas polish`  
No flags or arguments are accepted or honored.

Note that from time to time, this list of worlds will be extended (and perhaps trimmed).
Be careful when pulling the latest version of this code so as not to destroy your list of world names!
